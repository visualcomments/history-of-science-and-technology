# RUNBOOK — инциденты и восстановление

Основано на DESIGN §15.2. Классы инцидентов, владельцы и шаги восстановления.
Цели для учебного контура: **RPO ≤ 24 ч**, **RTO ≤ 8 ч**. Постмортем — без
поиска виновных; action items уходят в backlog.

Связанные документы: процедура эксперта — `docs/EXPERT-ASSIGNMENT.md`;
формат Hub-репозитория и откат публикации — `docs/HF-DATASET.md`.

## Общая схема реакции

1. Обнаружение (алерт Telegram / упавший CI) — фиксируем `run_id`/`task_id`.
2. Классификация инцидента по таблице ниже.
3. Владелец выполняет шаги; при 3 неудачах — эскалация человеку-координатору.
4. Запись в incident-лог, при необходимости — rollback.
5. Постмортем и action items.

---

## `data-corruption` — повреждение данных

**Владелец:** D2 (Dataset Core & Validation), консультант E1/E2.

1. Остановить публикацию (не мержить publish-PR).
2. Определить затронутые записи по `sha256` в провенанс-журнале.
3. Если причина — неверная оцифровка: создать новую запись со ссылкой
   `parent_record_id` (bronze неизменяем; исправления — новыми записями).
4. Перезапустить `python src/physics_ds/schema/validate.py` и доменные проверки.
5. Обновить dataset-версию (`v<MAJOR>.<MINOR>`) через PR и CHANGELOG.
6. Rollback при необходимости — HF revision / git revert.

## `copyright-breach` — нарушение авторских прав

**Владелец:** E3 (методология и copyright).

1. Немедленно снять артефакт с публикации (HF/Kaggle).
2. Найти запись и её `rights.basis`; переклассифицировать через
   `physics_ds.rights.classify`.
3. Если требовалось `metadata-only` — заменить содержимое на метаданные/факты,
   сканы/полный текст удалить из истории (перезапись релиза).
4. Провести аудит всех записей того же источника.
5. Обновить `PROVENANCE.md` / dataset card; зафиксировать постмортем.

## `pii-leak` — утечка персональных данных

**Владелец:** PM-агент + INFRA (немедленно), аудит — E3.

1. Немедленно отозвать затронутый публичный артефакт.
2. Удалить PII из репозитория и истории публикации.
3. Убедиться, что в публичных артефактах только role IDs (`Rxx`).
4. Прогнать PII-скан (regex + энтропия) на все публичные файлы.
5. Ротация затронутых токенов, если они могли утечь.

## `ci-outage` — недоступность CI

**Владелец:** INFRA.

1. Проверить статус GitHub Actions; если платформенный сбой — перевести
   задачи в `blocked` с причиной (graceful degradation, §6.4).
2. Не обходить гейты локальными коммитами в `main`.
3. Повторить запуск после восстановления; убедиться, что все гейты зелёные.

## `api-outage` — недоступность внешнего API

**Владелец:** D1 (Collection/Infra).

1. Пометить задачу `blocked` с указанием API и времени.
2. Использовать кэш/bronze-копию, если она валидна по `sha256`.
3. Не повторять запросы агрессивно (соблюдать ToS/rate-limit).
4. Возобновить после восстановления API.

## `cost-overrun` — превышение бюджета

**Владелец:** PM-агент + INFRA.

1. Остановить дорогостоящие запуски (GPU/обучение).
2. Проверить алерты на 70/90/100% лимита.
3. Перевести задачи на free-tier; при исчерпании — `blocked`, не тратить платные
   ресурсы (§16.3).
4. Пересмотреть бюджет и пороги алертов.

## Backup / retention

- bronze-манифесты — в object storage (S3/MinIO) + ежедневный снапшот.
- retention 90 дней.
- Проверка восстановления — при каждом milestone (M1–M4).
